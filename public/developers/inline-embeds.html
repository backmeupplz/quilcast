Inline mini app embeds

For developers. Quilcast, November 2026.

A mini app embed is a picture with a button, and the button opens the whole app. For small jobs, that's a lot: to vote in a poll, you open an app, wait for its splash, tap an option and close it again. An inline embed lets the app declare a small view of itself, which clients that support it run right in the cast, in place of the picture. In Quilcast, a poll's options are in the cast, and after you vote, so are its results.

The view is an ordinary page of your app, and it talks to the client with the same mini app SDK. It gets fewer calls than a whole app: enough to know who's reading and what cast it's in, to sign in, and to open the whole app for the rest. Clients that don't support inline embeds show the usual card, so nothing breaks anywhere.

1. Declare the view

Next to the fc:miniapp tag on your embed's page, add an fc:miniapp:inline tag:

<meta name="fc:miniapp" content='{"version":"1","imageUrl":"https://poll.example.com/p/8f3a.png",
  "button":{"title":"Vote","action":{"type":"launch_miniapp","name":"Poll","url":"https://poll.example.com/p/8f3a"}}}' />
<meta name="fc:miniapp:inline" content='{"url":"https://poll.example.com/p/8f3a?inline","height":156}' />
  • url is the page the client puts in the cast. It must be an https URL on the same origin as the app the embed launches (button.action.url, or the page itself). Clients ignore one that points anywhere else.
  • height is the view's height in CSS pixels. Clients hold it to 80-480. The width is the card's, which is about 300 to 600 pixels, so lay the view out to fit any width in that range.
  • The fc:miniapp tag stays as it is, and it's still required. Its picture is what clients without inline embeds show, and its button still opens the whole app. Clients that run your view show it as well, under the view.
  • The view has its own tag, not a field in fc:miniapp, so that the embed stays valid for every client and validator that checks it.

2. Build the view

Build it like any mini app page, with the SDK or the same messages without it, and keep it to one screen that never scrolls: a few buttons, a number, a result. The view shows as soon as its frame loads, without a splash screen, so draw your own background and keep the page light. Call sdk.actions.ready() as usual.

import { sdk } from '@farcaster/miniapp-sdk'

const ctx = await sdk.context
await sdk.actions.ready()

// ctx.client.inline: true when you're running in a cast (Quilcast's addition to the context)
// ctx.location: { type: 'cast_embed', embed, cast } in a cast; undefined in a composer's preview,
//   where the person is still writing the cast and the view can't be used
// ctx.user: the reader, or undefined when they aren't signed in to the client

A view can use these calls:

  • sdk.actions.signIn({ nonce }). The client asks the person first, as it does for a whole app. Verify the result on your server before you count anything (Build for Hypersnap has the whole check).
  • sdk.actions.openMiniApp({ url }) opens your whole app, or another one. Pass your embed's own URL (the one in button.action.url) to open your app for this cast, with the same cast_embed context. Do this for anything the view can't do.
  • sdk.actions.openUrl(url), sdk.actions.viewCast({ hash }) and sdk.actions.viewProfile({ fid }).
  • sdk.getCapabilities() lists these, so you can check for them.

Everything else is refused with an error: the wallet, composeCast, addMiniApp, notifications, the camera and microphone, haptics and the primary button. Those belong in the whole app, so open it with openMiniApp.

An example: Poll

poll.quilcast.com, Quilcast's own composer action, works this way. Each poll's page declares /p/<id>?inline as its view, 60 pixels plus 48 for each option. That URL is the same page laid out smaller: the options as buttons and the number of votes so far. Tapping an option asks to sign in, the sign-in is the vote, and the view shows the results. See actions/poll/ for the code.

Trust

  • The context isn't proof. Anyone can load your view, and ctx.user is whatever the client says. Count or store something for an account only after a sign-in you've checked.
  • What your view sees. It runs in a sandboxed frame on your origin. It sees the cast it's in and, if the reader is signed in, their FID and name. It can't post, can't use the wallet and can't send notifications.
  • When it loads. Loading a page tells its server who is reading (their IP address, and when). Quilcast loads views from its own hosts as you scroll to them, like its own pictures. A view from any other host loads only once you tap Load here on its card, so you can't count on it loading by itself.

For client developers

Any Farcaster or Hypersnap client that already runs mini apps can run inline embeds too. It takes five steps:

  1. Read the tag. When you unfurl a link whose page has a valid fc:miniapp (or fc:frame) with a launch_miniapp (or launch_frame) button, also read fc:miniapp:inline. Parse it as JSON, and take it only if url is https on the same origin as the button's app URL and height is a positive number, which you hold to 80-480. Otherwise draw the usual card.
  2. Put the view in the card. Draw an iframe of url in place of the embed picture, as wide as the card and height pixels tall, and keep the rest of the card under it, with its button opening the whole app. Give the frame sandbox="allow-scripts allow-same-origin allow-forms allow-popups allow-popups-to-escape-sandbox", referrerpolicy="no-referrer" and loading="lazy", and no allow permissions. Keep the same frame while the feed redraws, so that scrolling doesn't reload it.
  3. Answer it like a mini app, with fewer calls. The view speaks the SDK's Comlink messages over postMessage, like a whole app. Start listening before the frame loads, and take a message only when event.source is that frame's contentWindow and event.origin is the view's origin. Answer context with client.inline: true, location: { type: 'cast_embed', embed, cast } and the signed-in user. Answer ready, signIn, openUrl, openMiniApp, viewCast, viewProfile and getCapabilities, and refuse everything else with an error.
  4. Ask before signing in, outside the frame. Show your own prompt over the card or the screen, with the app's name and host, as you do for a whole app. The view can't draw over the prompt, and it never signs anything itself. The prompt comes up right where the person was tapping, so have its yes button ignore clicks for its first second, and refuse a second signIn while one prompt is up. When the view calls openMiniApp with its embed's URL, open the whole app with the same cast_embed location.
  5. Mind what loading tells the host. A frame that loads as the reader scrolls tells its host who's reading. Quilcast loads views from its own hosts right away and other hosts' only after a tap, showing the embed picture with a Load here button until then. Do the same, or let readers choose.

A native client does the same with a web view in the card, and answers the same messages it already answers for whole apps there (window.ReactNativeWebView in a React Native app), limited to the calls above.

In your composer, you can show the view as a preview of the cast being written: leave location out and keep the frame from taking clicks (pointer-events: none). Quilcast's code is in src/inline.ts (the calls) and InlineApp in src/ui.tsx (the card), and the tag is read in server/unfurl.mjs.

Test it

  1. Serve your app over https on a public address (a tunnel such as cloudflared tunnel --url http://localhost:5173 works while you build).
  2. Cast a link to your embed's page and open the cast in Quilcast. A view on your own host shows Load here first.
  3. Quilcast keeps a link's preview for an hour, so after you change the tags, add a query string to the link (?v=2) to see them at once.
